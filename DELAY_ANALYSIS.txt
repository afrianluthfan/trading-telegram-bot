EXECUTIVE SUMMARY

The 1-2 minute delay is caused by THREE layered bottlenecks:

1. PRIMARY (30+ seconds): Telegram API polling uses 30-second timeout
   - Location: src/telegram/bot.py, line 127
   - Issue: params={"timeout": 30, ...} blocks command processing

2. SECONDARY (1-4 seconds): Sequential bootstrap API calls on startup  
   - Location: src/main.py, lines 290-291
   - Issue: Sequential await calls instead of parallel

3. TERTIARY (1-4 seconds): Polling starts after bootstrap completes
   - Location: src/main.py, line 309
   - Issue: Polling task launched late in boot sequence

COMBINED EFFECT: 30s + 4s + 4s = 38+ seconds minimum, up to 120+ seconds
with slow networks or API delays.

PART 1: PRIMARY BOTTLENECK - THE 30-SECOND POLLING TIMEOUT

═══════════════════════════════════════════════════════════════════════════════════

FILE: /home/cashgen/trading-telegram-bot/src/telegram/bot.py
FUNCTION: start_polling() [lines 111-152]
CRITICAL LINE: 127

THE CODE:
```python
async def start_polling(self) -> None:
    """Long-polling loop for incoming Telegram commands."""
    if not self.enabled:
        log.info("Telegram bot disabled (no token/chat_id).")
        return

    self._running = True
    offset = 0

    log.info("Telegram bot polling started.")
    await self.send("Engine started. Awaiting signals.")

    while self._running:
        try:
            async with self._session.get(
                f"{self._base}/getUpdates",
                params={"timeout": 30, "offset": offset},  # ← LINE 127: CULPRIT
                timeout=aiohttp.ClientTimeout(total=45),
            ) as resp:
                data = await resp.json()  # ← BLOCKS HERE UP TO 30 SECONDS

            if not data.get("ok"):
                log.error(f"Telegram getUpdates error: {data}")
                await asyncio.sleep(2)
                continue

            for update in data.get("result", []):
                offset = update["update_id"] + 1
                msg = update.get("message") or update.get("edited_message")
                if not msg:
                    continue

                text = (msg.get("text") or "").strip()
                chat_id = msg["chat"]["id"]

                await self._handle_command(text, chat_id)  # ← User command processed here

        except asyncio.CancelledError:
            break
        except Exception:
            log.exception("Telegram polling error")
            await asyncio.sleep(2)
```

THE PROBLEM EXPLAINED:

The "timeout" parameter in line 127 is NOT the HTTP client timeout.
It's a SERVER-SIDE timeout sent to Telegram's API.

What happens:
1. Bot sends: GET /getUpdates?timeout=30
2. Telegram receives this and HOLDS the connection OPEN for 30 seconds
3. If messages arrive, Telegram returns them immediately
4. If NO messages arrive, Telegram waits the full 30 seconds, then returns empty
5. During these 30 seconds, the bot CANNOT process any commands

WORST-CASE TIMING:

T+0:00s   Bot starts
T+1:00s   Bootstrap API calls complete
T+3:00s   Telegram polling starts, sends first getUpdates(timeout=30)
T+3:00s   CONNECTION OPENED TO TELEGRAM, WILL WAIT UP TO 30 SECONDS
T+3:30s   USER SENDS /START COMMAND
          (Command received by Telegram, queued for next poll)
T+33:00s  30-second timeout EXPIRES
          getUpdates() finally returns with the queued /start command
T+33:10s  Bot processes /start command and sends response

RESULT: User waits 29.5 seconds from sending /start to receiving response ✓

PART 4: HOW THESE COMBINE TO CREATE 1-2 MINUTE DELAY

═══════════════════════════════════════════════════════════════════════════════════

SCENARIO: User starts bot and immediately sends /start

Normal network, 1 symbol:
T+0:00s    Bot starts
T+1:00s    Bootstrap API calls (1-2s for 4h, 1-2s for 5m) = ~2 seconds
T+3:00s    Polling task launches, sends getUpdates(timeout=30)
T+3:30s    User sends /start (command queued at Telegram)

Scenario with slow Binance API:
T+0:00s    Bot starts
T+1:00s    Bootstrap for 4h times out or retries (adds 10-20 seconds)
T+21:00s   Bootstrap for 5m (another 10-20 seconds)  
T+35:00s   Polling task launches, sends getUpdates(timeout=30)
T+35:30s   User sends /start
T+65:00s   30-second poll timeout expires
T+65:10s   Command processed
DELAY: ~30 seconds PLUS bootstrap delays = 60+ seconds

Scenario with two polling cycles:
T+0:00s    Bot starts
T+3:00s    First getUpdates(timeout=30) sent
T+10:00s   User sends /start (misses first poll if message arrives between checks)
T+33:00s   First poll returns (empty, or with message)
T+33:05s   Second getUpdates(timeout=30) sent
T+63:00s   Second poll timeout expires  
T+63:05s   Command finally processed (if message arrived after first poll)
DELAY: 53+ seconds

All three factors combined:
- 30s polling timeout
- 1-4s bootstrap delay
- 30s+ from slow API or retries
- Potential extra polling cycle
= 60-120+ seconds (1-2 minutes) ✓✓✓

PART 7: RECOMMENDED FIXES (PRIORITY ORDER)

═══════════════════════════════════════════════════════════════════════════════════

FIX #1: REDUCE POLLING TIMEOUT (HIGHEST PRIORITY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

File: src/telegram/bot.py
Line: 127
Impact: Reduces max /start delay from 30s to 5s (-25 seconds)
Difficulty: TRIVIAL (1-line change)

BEFORE:
```python
params={"timeout": 30, "offset": offset},
```

AFTER:
```python

```

WHY THIS WORKS:
- Reduces server-side polling timeout from 30 seconds to 5 seconds
- Bot checks Telegram for updates every 5 seconds instead of every 30
- User's /start command processed within 5 seconds maximum
- Minimal impact on API load (6 polls per minute vs 2)

BENEFITS:
- Instant 25-second improvement
- Zero code complexity
- No breaking changes
- Trade-off: Slightly more frequent API calls (acceptable)

FIX #2: PARALLELIZE BOOTSTRAP CALLS (HIGH PRIORITY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

File: src/main.py
Lines: 285-295
Impact: Reduces bootstrap time by 50% (-2-4 seconds)
Difficulty: LOW (restructure loop)

BEFORE:
```python
for sym in settings.symbol_list:
    buf = KlineBuffers(sym, on_candle_close=on_candle_close)
    buf.register_interval("4h", max_len=25)
    buf.register_interval("5m", max_len=10)

    await buf.bootstrap(client, "4h", limit=20)  # Waits here
    await buf.bootstrap(client, "5m", limit=3)   # Waits here

    buffers[sym] = buf
```

AFTER:
```python
bootstrap_tasks = []

for sym in settings.symbol_list:
    buf = KlineBuffers(sym, on_candle_close=on_candle_close)
    buf.register_interval("4h", max_len=25)
    buf.register_interval("5m", max_len=10)

    # Collect tasks without awaiting
    bootstrap_tasks.append(buf.bootstrap(client, "4h", limit=20))
    bootstrap_tasks.append(buf.bootstrap(client, "5m", limit=3))

    buffers[sym] = buf
    states[sym] = EngineState(symbol=sym)
    all_streams.extend(buf.stream_names)

# Run all bootstraps concurrently
await asyncio.gather(*bootstrap_tasks)
```

WHY THIS WORKS:
- All API calls run in parallel instead of sequentially
- With 1 symbol: 2 calls run at same time (halves duration)
- With 2 symbols: 4 calls run in parallel (4x faster)
- asyncio.gather() waits for all to complete before returning

BENEFITS:
- 2-4 seconds faster startup
- Lower chance of hitting timeout during boot
- Better resource utilization
- Trade-off: Higher Binance API load during startup (acceptable)

- Trade-off: Slightly more complex startup logic

CONCLUSION

The Telegram bot's /start command delay is caused by a combination of:

1. 30-second Telegram polling timeout (PRIMARY - 30+ seconds)
2. Sequential bootstrap API calls (SECONDARY - 1-4+ seconds)
3. Polling started after bootstrap (TERTIARY - 1-4 seconds)

The PRIMARY issue alone is responsible for most of the delay.

FIX #1 (reduce polling timeout from 30s to 5s) is recommended as the
quickest and most impactful solution, providing an immediate 80-90%
improvement in responsiveness.

Combined with FIX #2 (parallel bootstrap), startup response time can be
improved from 1-2 minutes to 5-15 seconds.
